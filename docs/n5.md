# N5: why D3D9 presents run below the refresh rate on NVIDIA hosts

On an NVIDIA host, each windowed D3D9 Present waited about 16 to 20 ms with
the guest CPU idle. The D3D9 probe reached about 39 fps on `Nvidia1`, while
`AMD1` and the Intel host reached about 60 ([`present.md`](present.md#what-remains)).
This page gives the cause, a host-side fix with its proof, and what remains.
Evidence paths are relative to [`docs/evidence/n5/`](evidence/n5/).

helios: QEMU at the VMLabDev/qemu commit `d8a6048aae` (the `Nvidia1`
`qemu_binary`), virglrenderer 1.3.0, NVIDIA 610.57.04, RADV (Mesa 26.2.2),
vmlab 0.28.0-alpha. The guest was `windows-11` with the package built from
`82d8e51`. Other workers' VMs shared `Nvidia1` throughout, one or two at a
time (`win3d-shaders2-dev`, later `win3d-d3d12app-nv1`). No measurement was
taken with `Nvidia1` idle, so the absolute frame rates below vary by about
±8 fps from run to run. The fence latencies do not vary that much.

## Result

| Run on `Nvidia1`, same guest disk | Venus ring-1 fence latency, p50 | D3D9 probe (`pace d3d9`) | `pace d3d9-imm` |
| --- | --- | --- | --- |
| Stock render server | 10.21 ms | 36.9 per second | 42.8 per second |
| Vulkan layer that strips SYNC_FD export from fences | 1.68 ms | 53.1 per second | 159.4 per second |
| Render server built with the virglrenderer patch | 1.20 ms | 46.8 per second | 109.8 per second |

The two fixed runs remove the 10 ms floor. They differ from each other by
less than the run-to-run noise on the shared GPU. The patched run lost
4 seconds to a guest stall: its 20-second case took 24.2 s.

## Cause

virglrenderer's Venus renderer retires each ring-indexed virtio fence
through a queue-sync thread. `vkr_queue_sync_submit()` submits an empty
batch with a `VkFence` and the thread waits on that fence with
`vkWaitForFences`. `vkr_device_alloc_queue_sync()` creates the fence
exportable as a SYNC_FD (`VkExportFenceCreateInfo`) whenever the device has
`VK_KHR_external_fence_fd`. Nothing ever exports these fences.

On NVIDIA 610.57.04, `vkWaitForFences` on an exportable fence wakes up to
about 10 ms after the fence signals. On a plain fence it wakes within about
0.3 ms. RADV shows no difference (`host/vkfence.txt`):

| Fence | RTX 5090: mean, max wake-up | RADV: mean, max wake-up |
| --- | --- | --- |
| Plain | 0.28 ms, 10.7 ms (1 of 200 over 5 ms) | 1.24 ms, 9.2 ms |
| Exportable SYNC_FD, as vkr creates it | 7.42 ms, 10.8 ms (144 of 200 over 5 ms) | 1.18 ms, 7.3 ms |

Every DMA buffer that the guest UMD submits on a Venus context ends with a
ring-1 fence (`VIOGPU_CMD_SUBMIT_TIMELINE`). The KMD reports the DMA buffer
complete when that fence returns. On NVIDIA, each one therefore takes at
least 10 ms. A windowed D3D9 Present is a Blt present (`present.md`), and
it needs two such completions in series:

1. The producer context's render DMA buffer completes. That signals the
   monitored fence that the UMD's scheduled Present makes the present
   context wait on (`gdikmt_d3dddi_reserve_present` and `signal_present`).
2. The present context's DMA buffer completes. The KMD does the CPU copy in
   that buffer.

The D3D9 runtime then locks the allocation for the redirected blit and
waits for both buffers (`VIDMM_BEGINCPUACCESS_WAIT`). Two floors of 10 ms
each, plus the vblank wait at interval one, gave about 21 ms per frame.
DWM's own DMA buffers have the same floor, so DWM also composed at only 41
to 55 frames per second.

AMD and Intel hosts never showed this, because their drivers wake
exportable fences promptly.

## How it was found

1. **UMD timing** (`guest/umd-timing-*.txt`). This was a diagnostic build
   of the UMD with per-call timers, the patch in
   `src/umd-present-timing.diff`, enabled by
   `D3D10UMD_YTTRIUM_PTIME=<file>`. Almost all of a D3D9 Present was the
   runtime's `pfnPresentCb`: 13.6 to 24.5 ms per call at interval one, and
   18.2 ms at interval immediate. The UMD made no CPU fence waits:
   `feedback_wait` and the `Sleep(1)` back-offs never showed. With
   `D3D10UMD_YTTRIUM_SCHEDULED_PRESENT=0`, `pfnPresentCb` took 7.8 ms, but
   the runtime then blocked elsewhere, and the probe still ran at
   36.8 fps.
2. **Guest round trips.** A Venus submit plus fence wait took 0.03 ms
   (`guest/vk_rtt.txt`), because Venus waits on its fences in the guest. A
   D3D11 event query took 0.5 ms at p50 (`guest/d3d11_rtt.txt`). The host
   GPU was not slow.
3. **DxgKrnl ETW in the guest** (`logman`, `tracerpt`;
   `guest/etw-dxgkrnl-dma-latency.txt`). Every DMA buffer on every context
   (the probe's producer and present contexts, and DWM) took at least
   10.4 ms from submission to `DXGK_INTERRUPT_DMA_COMPLETED`: p10
   10.50 ms, p50 10.87 ms. Completions arrived in bunches about 10 to 12 ms
   apart. The guest KMD has no 10 ms timer.
4. **The VM under a QEMU this worker owned** (`src/run-qemu.sh`). With the
   lab down, the same disk booted under the same QEMU binary with the same
   devices, plus QEMU trace events. A logon script in the guest ran the
   probe and shut Windows down. QEMU's `virtio_gpu_fence_ctrl` and
   `virtio_gpu_fence_resp` (`selfrun/nv1-a-qemu-fence-trace.txt`) put
   `SUBMIT_3D` fences into two groups: 13,173 answered within 1 ms and
   4,424 at 10.0 to 10.9 ms.
5. **An `LD_PRELOAD` shim on QEMU** (`src/shim.c`,
   `selfrun/nv1-c-shim-fence-latency.txt`). The shim timed each fence from
   its creation to virglrenderer's callback. Context-0 fences took 0.04 ms.
   Ring-0 context fences took 0.04 ms. Ring-1 (GPU timeline) context fences
   took 10.21 ms at p50, with p10 10.14 ms. QEMU was already running with
   `VIRGL_RENDERER_ASYNC_FENCE_CB | THREAD_SYNC` (flags `0x342`), so QEMU's
   10 ms fence-poll timer was not the cause. The delay was in the render
   server, between its queue-sync submit and the callback.
6. **Host Vulkan** (`src/vkfence.c`). The exportable fence in the table
   above reproduces the delay outside QEMU. A GL fence used the way vrend
   uses it (`src/glfence.c`) woke within 0.4 ms on NVIDIA.
7. **Proof.** `src/layer.c` is a Vulkan implicit layer that drops
   `VkExportFenceCreateInfo` from `vkCreateFence`. It lowered the ring-1
   fence latency to 1.68 ms (`selfrun/nv1-d-*`). A render server built
   from 1.3.0 plus
   [`patches/host/virglrenderer/0002`](../patches/host/virglrenderer/0002-vkr-do-not-create-queue-sync-fences-exportable.patch)
   and started through `RENDER_SERVER_EXEC_PATH` lowered it to 1.20 ms
   (`selfrun/nv1-e-*`). The results table above has both runs.

## Fix

The fix belongs on the host. The guest needs no change.
[`patches/host/virglrenderer/0002`](../patches/host/virglrenderer/0002-vkr-do-not-create-queue-sync-fences-exportable.patch)
creates the queue-sync fence without export info. vkr's only
`vkGetFenceFdKHR` call is in `vkResetFenceResourceMESA`, which receives
guest-created fences and never these.

This worker did not apply the patch, and it is not in the package.
Decision D3 keeps helios's host stack at the stock virglrenderer 1.3.0.
This worker's slot covers only the Mesa and KMD patches. No guest-side
change can remove the floor:

- every DMA buffer completion waits for this host fence;
- the D3D9 runtime waits on DMA completion of the back buffer before it
  blits.

To deploy the fix, choose one of these:

- Add the patch to `patches/host/virglrenderer/`, outside `workaround/`,
  and build it with `patches/host/build-virglrenderer.sh`. Then give
  QEMU's environment `RENDER_SERVER_EXEC_PATH` for the NVIDIA GPU
  profiles. This needs vmlab to pass environment variables per host GPU,
  as it already does for `VK_LOADER_DRIVERS_SELECT`.
- Send it to virglrenderer upstream, or report the slow wake-up on
  exportable fences to NVIDIA. Under decision D4, upstreaming is for the
  user to decide.

## What remains

- **The fix is not deployed.** Packaged D3D9 on NVIDIA hosts stays at
  about 40 fps until the host's render server carries the patch.
- **No 12-of-12 run with the fix.** Nothing in the package changed, so the
  package's e2e results stand. A run with the patched render server needs
  vmlab to start QEMU with `RENDER_SERVER_EXEC_PATH`. The self-run QEMU
  had no agent channel, so `tests/e2e/run.sh` cannot drive it.
- **Frame rates on a quiet GPU.** Other workers' VMs shared `Nvidia1` in
  every run. The patched D3D9 runs reached 47 to 53 fps, with about one
  frame in 20 missing a vblank (p95 28 to 34 ms).
- **Issue 2 of the brief was not done.** That issue is Windows 10 on
  `AMD1` with Blender, plus a `gl_alpha` repro that reproduces the
  translucency. `AMD1` stayed at the three-VM limit for the whole time
  box, and the time went to N5. A WGL build without `0027`, for a
  `gl_alpha` A/B, was built but not run. One untested idea for `gl_alpha`:
  Blender's pixel format may have no alpha bits, while `gl_alpha` asks
  for 8.
