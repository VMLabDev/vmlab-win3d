# DirectDraw 16 bpp modes for 64-bit programs: why there are none

A 64-bit DirectDraw program on this stack cannot set a 16 bpp display
mode. `SetDisplayMode(640, 480, 16)` fails with `DDERR_UNSUPPORTED`
(`0x80004001`), and `EnumDisplayModes` lists 32-bit modes only. 32-bit
programs get 8, 16 and 32 bpp ([`ddraw.md`](ddraw.md#16-bpp-modes)). This
page traces where Windows decides that, and shows that neither our UMD nor
our KMD can change it. **The brief's fix was not possible.** No patch was
added, and the acceptance run (`SetDisplayMode(640,480,16)` and 300 flips
from a 64-bit program) was not met. The work ran on 2026-10-19 on helios,
on AMD1, with the `x86_64/windows-11@26100.1742.5` template (Windows 11
24H2, build 26100.1742). The evidence is in `docs/evidence/dd16/`.

## Result

| Question | Answer | Evidence |
| --- | --- | --- |
| Where does 64-bit `ddraw.dll` get its modes? | `EnumDisplaySettingsA`, from win32k. `SetDisplayMode` calls `ChangeDisplaySettingsExA`. There is no emulation of other depths in 64-bit `ddraw.dll` | `DD_EnumDisplayModes4`, `mySetMode` in `System32\ddraw.dll` |
| Where do 32-bit programs' 16 bpp modes come from? | From the `DWM8And16Bit` low-colour mitigation. 32-bit `user32.dll` calls it when the kernel's mode list runs out, and it appends emulated 8 and 16 bpp modes. 32-bit `ddraw.dll` calls it too. 64-bit `user32.dll`, `ddraw.dll` and `apphelp.dll` have none of this code | `EnumDisplaySettingsExW` in `SysWOW64\user32.dll`; `DWM8And16Bit_*` exports: 6 in `SysWOW64\apphelp.dll`, 0 in `System32\apphelp.dll` |
| Can the KMD offer a real 16 bpp mode? | No. `dxgkrnl.sys` drops every source mode whose format is R8G8B8, R5G6B5, X1R5G5B5, A1R5G5B5 or P8 when it builds the display mode list. It also refuses a VidPN with such a source mode before it asks the driver | `OBTAIN_MODES_ON_SOURCE::operator()`, `VIDPN_MGR::_IsSupportedVidPn`, `DmmIsAllSourcesPixelFormatValid` |
| Does that hold for our KMD? | Yes. With R5G6B5 source modes in every VidPN source mode set, `D3DKMTGetDisplayModeList` still returns only A8R8G8B8 and A8B8G8R8 modes, and the 64-bit mode lists are unchanged | `amd1/kmd-r5g6b5/modeprobe-x64.json` |
| Can the UMD help? | No. Its `GetCaps` already reports R5G6B5 as a display format: 64-bit D3D9 `CheckDeviceType(HAL, R5G6B5, R5G6B5, fullscreen)` returns `D3D_OK`. Every mode list comes from the kernel, which the UMD does not reach. D3D9's `EnumAdapterModes` reads `D3DKMTGetDisplayModeList`, which has no 16-bit modes (0 R5G6B5 modes in a 64-bit process, 19 in a 32-bit one) | `amd1/baseline/modeprobe-{x64,x86}.json` |

## How each layer decides

The mode list a program sees passes through these layers. The function
names come from Microsoft's public symbols for the template's binaries
(`analysis/binaries.txt`). `analysis/analyse.sh` repeats the decompilation.

1. **`ddraw.dll` (64-bit).** `DD_EnumDisplayModes4` loops over
   `EnumDisplaySettingsA(device, i)`. It drops `MODEX` and `VGA` entries,
   maps 15 bpp to 16, and removes duplicates. `mySetMode` fills a `DEVMODE`
   and calls `ChangeDisplaySettingsExA`. Neither function adds a mode that
   GDI does not list.
2. **`user32.dll`.** The 64-bit `EnumDisplaySettingsExW` is a direct call
   to `NtUserEnumDisplaySettings`. The 32-bit one does the same, but when the
   kernel returns an error (the end of the list) and the mode is not
   `ENUM_CURRENT_SETTINGS` or `ENUM_REGISTRY_SETTINGS`, it loads
   `apphelp.dll` and calls `DWM8And16Bit_IsShimApplied_CallOut` and
   `DWM8And16Bit_EnumDisplaySettingsExW_CallOut`. Those add the emulated
   8 and 16 bpp modes. `ChangeDisplaySettingsExW`, `RestoreDisplayMode`
   and `DirectDrawCreate[Ex]` have matching call-outs. The WOW64 thunk
   (`whNtUserEnumDisplaySettings` in `wow64win.dll`) only marshals the
   arguments.
3. **`win32kbase.sys`.** `DrvEnumDisplaySettings` returns entries from a
   per-device list, `DrvBuildDevmodeList`. It does not check the caller's
   bitness. That list comes from the display driver's `DrvGetModes`
   (`ldevGetDriverModes`), and `PruneModesByDisplayDeviceCaps` and
   `PruneMode` prune it by monitor timing, not by depth. `EDS_RAWMODE`
   returns the same 38 entries as a plain enumeration.
4. **`cdd.dll`.** On WDDM, `DrvGetModes` is the Canonical Display Driver's.
   It asks `dxgkrnl` for the source's mode list and keeps formats
   A8R8G8B8, R8G8B8, R5G6B5 and P8. CDD would pass a 16-bit mode through.
5. **`dxgkrnl.sys`.** `OBTAIN_MODES_ON_SOURCE::operator()` walks the
   cofunctional VidPN source modes and calls `_AddMode` only when the
   format is not in the set `0x20003900000` (bits 20, 23, 24, 25 and 41:
   R8G8B8, R5G6B5, X1R5G5B5, A1R5G5B5 and P8). `VIDPN_MGR::_IsSupportedVidPn`
   calls `DmmIsAllSourcesPixelFormatValid` with the same mask and reports
   the VidPN unsupported without calling `DxgkDdiIsSupportedVidPn`. The only
   exception is the copy that the enumeration itself pins. So a WDDM driver's
   low-colour source modes neither reach the mode list nor can be committed.

The mode list therefore has 32-bit modes only, whatever the driver offers.
Since Windows 8, the OS gives low-colour depths to programs only through
the 32-bit `DWM8And16Bit` emulation.

## Measurements

`modeprobe` (`src/modeprobe.c`) prints every mode list a process can see:
`EnumDisplaySettingsEx` (plain and `EDS_RAWMODE`),
`ChangeDisplaySettingsEx(640x480x16, CDS_TEST)`, D3D9 `GetAdapterModeCount`
and `CheckDeviceType`, DirectDraw `EnumDisplayModes` and, with `--set`,
`SetDisplayMode(640, 480, 16)`, and the raw `D3DKMTGetDisplayModeList` with
each mode's D3DDDI format. Lab `win3d-dd16-amd1` on AMD1 ran
`tests/e2e/run.sh --keep` (the package at `82d8e51`) and then
`run-guest.sh`.

| Source | x64, package as built | x86, package as built | x64, KMD with R5G6B5 source modes |
| --- | --- | --- | --- |
| `D3DKMTGetDisplayModeList` | 152 modes: 76 A8R8G8B8 (21), 76 A8B8G8R8 (32) | The same 152 | The same 152; no R5G6B5 (23) |
| `EnumDisplaySettingsEx` (also `EDS_RAWMODE`) | 38, all 32 bpp | 114: 38 each at 8, 16 and 32 bpp | 38, all 32 bpp |
| `ChangeDisplaySettingsEx(640x480x16, CDS_TEST)` | `-2` (`DISP_CHANGE_BADMODE`) | `0` (`DISP_CHANGE_SUCCESSFUL`) | `-2` |
| D3D9 R5G6B5 adapter modes | 0 | 19 | 0 |
| D3D9 `CheckDeviceType` R5G6B5 fullscreen | `D3D_OK` | `D3D_OK` | `D3D_OK` |
| DirectDraw `EnumDisplayModes` | 19, all 32 bpp | 57: 19 each at 8, 16 and 32 bpp | 19, all 32 bpp |
| DirectDraw `SetDisplayMode(640, 480, 16)` | — | — | `0x80004001` (`DDERR_UNSUPPORTED`) |

The R5G6B5 KMD is `docs/evidence/ddraw/kmd-16bpp-experiment/0003-kmd-16bpp-source-modes.patch`
on top of `patches/kmd/0001` and `0002`. It was built, signed and installed
over the package for this run only (`amd1/kmd-r5g6b5/installed-kmd.txt`).
The desktop stayed at 1280×800×32 throughout. The earlier experiment on
Nvidia1 showed the same 64-bit result
(`docs/evidence/ddraw/kmd-16bpp-experiment/ddfull-x64.json`). It also
checked only `EnumDisplaySettings` and DirectDraw; this run adds the kernel's
own list. Nothing in this path depends on the host GPU, so no NVIDIA lab
was run for this page.

The baseline `tests/e2e/run.sh` in that lab passed 11 of 12
(`amd1/baseline/e2e-results.txt`). Direct3D 12 x86 failed because the
probe window was not in any console capture. That run has no change from
this work, and the result is recorded only as the state of the lab.

## What remains

- A 64-bit program that insists on 16 bpp has no path on Windows 10 or 11,
  on this driver or any other WDDM driver. The limit is in `dxgkrnl.sys`
  and in the absence of a 64-bit `DWM8And16Bit` emulation. We know of no
  such program. 16-bit games are 32-bit programs, and they get their modes
  ([`ddraw.md`](ddraw.md)).
- The only way around it would be to emulate the mode inside the process:
  hook `EnumDisplaySettings` and `ChangeDisplaySettings`, or replace
  `ddraw.dll` system-wide, as the 32-bit mitigation does. That is not a
  driver change, and it would put a per-process hook into every 64-bit
  program, so this work did not try it.
